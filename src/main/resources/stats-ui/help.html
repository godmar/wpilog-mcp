How the stats are computed A short reference for the numbers shown on the summary and per-log pages.

Match-window filtering

All current and battery statistics are computed over the match window only — from the moment the robot first becomes enabled by the Driver Station to the final disable after teleop. Pre-match idle (the several minutes many logs spend sitting on the field before a match) is excluded so it doesn't dilute the numbers.

The match window is derived from the DriverStation Enabled and Autonomous booleans in the log, with the usual FMS quirks handled:

  • The FMS sets Autonomous=true slightly before Enabled=true during the pre-match countdown. We count the auto phase as starting only when both are true.
  • Between auto and teleop there is a ~2 s disabled gap on an FMS. Teleop start is detected as the first re-enable after auto ends (or at auto end itself in practice mode, where the robot stays enabled through the boundary).
  • Match end is the first Enabled=false strictly after teleop start. If the log was cut off with the robot still enabled, match end falls back to the last timestamp in the log.
Time-series charts: the chart x-axes are clipped to this window with about five seconds of padding on each side, so you can see the moment the robot came alive and the moment it went back to disabled without the huge pre-match flat line in the way. The underlying time series itself is not trimmed — hover values outside the visible range are still real data.

Total current: mean, peak, P90

The summary page reports three rolled-up figures for "what the battery saw":

  • Mean total current — the average total draw across the match window.
  • Peak total current — the single largest instantaneous total draw observed at any moment during the match window. This is the number that should be compared against battery peak-current limits.
  • P90 total current — the 90th percentile of the instantaneous total. A "realistic sustained worst-case" figure — far more conservative than peak and far less susceptible to being moved by a single outlier spike.

All three are computed over a single aligned total-current time series built from the individual subsystems, not by aggregating per-subsystem statistics.

Why we can't just sum per-subsystem peaks

Each subsystem on the robot is logged independently. Direct supplyCurrentAmps entries (AdvantageKit-style) are only written when the value changes, so their samples are sparse and irregular. Swerve modules do not log supply current directly — we derive it per module from driveAppliedVolts, driveCurrentAmps, turnAppliedVolts, turnCurrentAmps, and the battery voltage, sampled at the drive-current timestamps. Those timestamps differ from one module to another.

A previous version of this app reported peakTotal = sum(per-subsystem peak). That number is almost always physically impossible, because each subsystem's peak occurs at a different moment. A swerve module might spike during an acceleration, the shooter during a fire, the climber during an end-of- match hang — and summing those unrelated extremes gives a number much larger than the robot ever actually drew at any single instant. On one real match log this produced ~1034 A of "peak total current" — comfortably above what an FRC battery can physically supply.

The fix: build a real total-current time series by aligning every subsystem onto a common time grid, and compute the statistics over that series. The peak then answers the right question — "what was the largest total draw at any single instant during the match?" — and lands in the physically plausible 200–400 A range for a typical FRC match.

The alignment algorithm

The inputs are one sample stream per subsystem, each already filtered to the match window. The output is one aligned sample per distinct timestamp across all streams.

Step 1 — union grid with zero-order hold

The output grid is the union of all input timestamps. Every moment at which any subsystem produced a sample becomes one output sample. Between updates, each subsystem is held at its most recently observed value (zero-order hold). This is both exact (no interpolation artifacts) and efficient — we don't create redundant samples for subsystems whose values aren't changing.

A subsystem that has not yet produced any sample at a given time contributes 0. This is the honest choice: we have no evidence it was drawing current before its first reported value. The practical effect is usually zero, because match-window filtering already aligns everything to roughly the same start point.

Step 2 — k-way merge

The merge is a straightforward k-way scan: 

cursor[i] = 0            // next unread sample index in stream i
held[i]   = 0.0          // current zero-order-hold value for stream i

while any stream still has samples:
    nextT = min(stream[i][cursor[i]].t across active streams)

    # Advance every stream whose next sample is at this timestamp.
    for each stream i:
        while cursor[i] < len(stream[i]) and
              stream[i][cursor[i]].t == nextT:
            held[i] = stream[i][cursor[i]].v
            cursor[i] += 1

    total = sum(held)
    output.append((nextT, total))

Complexity is O(N·k) where N is the total number of input samples and k is the subsystem count. With typical k ≈ 10–20 and N ≈ 50k per log this runs in well under a millisecond per match.

Step 3 — statistics over the aligned series

The aligned series is then handed to the same statistics helper the analyzer uses for individual subsystems, producing mean, peak, RMS, standard deviation, and P90. Those become the meanTotalCurrent, peakTotalCurrent, and p90TotalCurrent fields on the summary.

Stat definitions

The per-subsystem "Mean", "Peak", "P90", "StdDev", and "RMS" columns in the subsystem tables use the standard textbook definitions, computed over each subsystem's match-window samples:

  • Mean — arithmetic mean of the sample values.
  • Peak — maximum sample value.
  • P90 — 90th percentile with linear interpolation between ranks (numpy's default method): rank r = 0.9·(n-1), then interpolate between values[floor(r)] and values[ceil(r)].
  • StdDev — sample standard deviation with Bessel's correction (n-1 denominator).
  • RMS — root mean square of the sample values.

Caveats & known limitations

  • Sample-weighted, not time-weighted. The mean and percentiles treat each aligned sample equally, regardless of how much real time it represents. A subsystem logged at 40 Hz contributes many more "votes" to the mean than one that changes five times per match. This is consistent with how the per-subsystem stats work, and in practice the answer is within a few percent of a strictly time-integrated mean for well-behaved logs.
  • AdvantageKit delta logging. Direct subsystems using AdvantageKit's supplyCurrentAmps outputs are logged on-change, so their samples naturally cluster inside the match window. Filtering these to the match window removes only a handful of points. Swerve driveCurrentAmps, by contrast, is logged continuously at ~40 Hz from boot — so match-window filtering removes the bulk of pre-match idle samples and dramatically changes swerve's mean/P90. That's expected, not a bug.
  • Swerve supply current is derived. Swerve modules don't log supply current directly. We compute it per module as supply = (|driveAppliedVolts| · driveCurrentAmps + |turnAppliedVolts · turnCurrentAmps|) / batteryVoltage sampled at the drive-current timestamps, with battery voltage held from the nearest earlier sample.
  • Phase-detection fallback. If the DriverStation Enabled / Autonomous entries are missing or malformed and the match window can't be determined, the match-window filter is bypassed and statistics fall back to the full log span. The summary UI always shows the match boundaries it found, so you can tell when this has happened.
  • Sim logs are excluded. Files whose name contains _sim (case-insensitive) are skipped entirely from listings and aggregates. Simulated telemetry contains synthetic entries that don't exist on the real robot and would pollute event dashboards.
